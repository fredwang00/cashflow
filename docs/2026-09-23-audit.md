## Existing data still needs reconciliation

The read-only inspection found:

- One Amex transaction matching a card-payment description still included in spending. Reimporting with the fixed parser does not delete it.
- Sixteen checking rows have historical `canonical_id` links. Some may be genuine duplicate exports; the old heuristic cannot establish this. Do not blindly unlink all sixteen.
- No `ingest_state` history. New imports now create it; prior import dates cannot be reconstructed from the newest transaction date.
- No transactions after July 10 and no payroll after May 29. Missing months displayed as zero are not evidence of low spending or financial surplus.
- Eighty-four Amazon item records, none linked. Imported item details do not currently enrich the dashboard.

Preserve a consistent SQLite backup before correcting these records. Compare original exports to the current rows on a copy; retain valid categories, one-off labels and reimbursement adjustments. Reimport full-year exports to recover omitted refunds, and separately remove verified payment entries and incorrect historical duplicate links. Previously imported pending authorizations also require comparison to settled activity because export status was not stored.

## Limits that need explicit decisions or source evidence

- BofA cards/checking accounts share aggregate account names. Chase Freedom filenames must contain `freedom`; other Chase exports map to Prime Visa. Do not claim per-card completeness from those buckets.
- Several source IDs are derived from date/description/amount, not authoritative bank identifiers. Exact repeated purchases can be indistinguishable; description changes can produce duplicate IDs or conflicting records. New conflict checks prevent silent overwrites but cannot reconstruct missing identity. Changing the hash without a migration would duplicate existing history.
- Checking recognizes one configured payroll pattern and omits other positive deposits. Income is not a household balance sheet. PayPal covers debit rows only, not all refunds/currencies/funding paths. Reconcile these against statements if needed.
- Expense matching still uses date/amount, not proof of merchant identity or reimbursement receipt. Unique PayPal matches remain heuristic. Amazon cannot detect a future second shipment charge before it is imported.
- The current annual-fee report is a historical estimate, not a current issuer quote or complete subscription inventory. Verify renewal dates and retention/product-change terms directly.
- The local dashboard has write controls and binds to localhost. The historical LAN/read-only design is not current functionality.

## Historical documentation traps

Plans/specs are archived intent, not executable instructions. In particular, do not restore their refund-dropping parser examples, flag-only reimbursement calculations, or proposed email/download commands. The foundation's fixture smoke commands would write fake transactions to the default database unless a temporary `--db` is supplied. Its December-only fixture/March YTD example and the design's annual-goal pacing example are inconsistent. Its `AUTOINCREMENT` example also contradicts a table-count assertion because SQLite adds `sqlite_sequence`.

Multi-item Amazon prices remain unknown (stored as zero); they are not measured item prices. The proposed sinking-goal calculation assumes a creation date that the schema lacks. Any future SQLite synchronization must use a consistent backup, not copy a database during writes. The untracked expense-report plan is likewise superseded by partial-reimbursement storage and should not be replayed as a migration.
