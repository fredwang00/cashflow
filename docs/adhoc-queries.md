# Ad hoc queries

How to answer one-off questions ("were we charged for September?", "how much did we spend at Costco last year?") directly against the SQLite database, without writing new code.

## Opening the database

The database lives outside the repo at `~/.cashflow/cashflow.db` (override with `cashflow --db PATH`).

```bash
sqlite3 ~/.cashflow/cashflow.db          # interactive shell
sqlite3 ~/.cashflow/cashflow.db ".tables"
sqlite3 -header -column ~/.cashflow/cashflow.db "SELECT ..."
```

Read-only by default is safest: `sqlite3 "file:$HOME/.cashflow/cashflow.db?mode=ro"` (URI filenames need `.open` or the `-readonly` flag: `sqlite3 -readonly ~/.cashflow/cashflow.db`).

Python equivalent, used by the CLI and dashboard:

```python
import os, sqlite3
conn = sqlite3.connect(os.path.expanduser("~/.cashflow/cashflow.db"))
conn.row_factory = sqlite3.Row
```

## Schema cheat sheet

Full DDL is in `src/cashflow/db.py`. The tables that matter for queries:

| Table | Purpose |
|-------|---------|
| `transactions` | Charges, refunds, reimbursement offsets. One row per bank line item. |
| `amazon_items` | Amazon order items, optionally linked to a transaction via `transaction_id`. |
| `income` | Paycheck deposits (separate table, not negative transactions). |
| `categories` | `parent_id` hierarchy; `type` is `necessity` or `want`. |
| `accounts` | One bucket per export flavor (e.g. all BofA cards share one). |
| `merchant_rules` | `pattern` → `category_id`, source `manual` or `learned`. |
| `goals` | `ceiling` (monthly) and `surplus` (yearly) targets. |
| `possible_dupes` (view) | Pairs of charges that may be the same purchase recorded twice (same amount, fuzzy merchant, ≤3 days apart). Advisory review list, not confirmed duplicates. |

### `transactions` column semantics

- **Amounts are signed**: charges are **positive**, refunds/credits are **negative**. There is no separate type column.
- **`canonical_id`** — set when a row is a duplicate/superseded copy of the transaction it points at. Always filter `WHERE canonical_id IS NULL` or you double-count.
- **`is_reimbursed` / `reimbursed_amount`** — the effective cost is `amount - reimbursed_amount` (e.g. a $400 charge with a $400 employer reimbursement costs $0).
- **`is_one_off` / `one_off_label`** — baseline vs one-off split used by the dashboard trend chart.
- **`status`** — `pending` (needs review) or `confirmed`.
- **`who`** — `fred`, `wife`, or `shared`.
- **Dates** are ISO strings; use `strftime('%Y', date)` / `strftime('%m', date)`, or plain string comparison `date >= '2026-09-01'`.

### The savings exclusion

Spending numbers deliberately exclude money moved into savings/investments. The canonical condition is generated by `not_savings()` in `src/cashflow/queries.py` (currently `Crypto/Investments`, `Investments`, `College Savings`, plus uncategorized transactions which always count). Mirror it in ad hoc SQL:

```sql
SELECT t.id, t.date, t.amount, t.merchant
FROM transactions t
WHERE t.canonical_id IS NULL
  AND amount > 0
  AND (t.category_id IS NULL OR t.category_id NOT IN
       (SELECT id FROM categories WHERE name IN ('Crypto/Investments','Investments','College Savings')));
```

If you skip it, your totals will be higher than `cashflow status` and the dashboard.

## The accounts table is the card-to-person map

`transactions.account_id` is an integer FK into `accounts` — there is **no `account` column** (a classic mistake when writing SQL from memory). Join `accounts` to get the card, which is how you attribute a purchase to a person:

| Account | Whose card |
|---------|------------|
| `Capital One Venture` | Fred |
| `Capital One Wendy` | Wendy |
| `Capital One` | shared Capital One card |
| `Amex Gold` | Fred |
| `Robinhood Gold` | Wendy |
| `Bank of America` | shared bucket — all BofA cards merged, cannot distinguish cardholders |

```sql
SELECT t.date, t.merchant, t.amount, a.name AS account, t.who
FROM transactions t JOIN accounts a ON t.account_id = a.id
WHERE t.canonical_id IS NULL
  AND LOWER(t.merchant) LIKE '%dapper%'
ORDER BY t.date;
```

The `who` column (`fred`/`wife`/`shared`) is per-transaction and often `shared`; the account join is usually the stronger attribution signal.

## Copy-paste recipes

### Spending by merchant, most recent month with data

```sql
SELECT merchant, ROUND(SUM(amount - reimbursed_amount), 2) AS total, COUNT(*) AS n
FROM transactions
WHERE canonical_id IS NULL
  AND (category_id IS NULL OR category_id NOT IN
       (SELECT id FROM categories WHERE name IN ('Crypto/Investments','Investments','College Savings')))
  AND amount > 0
GROUP BY merchant ORDER BY total DESC LIMIT 25;
```

### Monthly spend in one category (trend across the year)

```sql
SELECT strftime('%Y-%m', date) AS month, ROUND(SUM(amount - reimbursed_amount), 2) AS total
FROM transactions
WHERE canonical_id IS NULL
  AND category_id = (SELECT id FROM categories WHERE name = 'Groceries')
GROUP BY month ORDER BY month;
```

### Find every charge from a merchant (e.g. "were we charged in Aug/Sept?")

```sql
SELECT t.date, t.amount, t.merchant, t.description, a.name AS account, c.name AS category
FROM transactions t
JOIN accounts a ON t.account_id = a.id
LEFT JOIN categories c ON t.category_id = c.id
WHERE LOWER(t.merchant) LIKE '%wendy-suspect-merchant%'   -- substring, case-insensitive
  AND t.canonical_id IS NULL
ORDER BY t.date;
```

Or skip SQL entirely with the CLI filters:

```bash
cashflow find "suspect-merchant" --date-from 2026-08-01 --date-to 2026-09-30 --json
cashflow find "barber" --min-amount 20 --max-amount 60 --who fred --account venture
```

### Discover merchant variants before querying a vendor

The same vendor arrives under many names (`TOWN CENTER BARBER SHO`, `Town Center Barber Shop`, `Town Center Barber Svirginia Beac Va`). Always discover variants first, or a date-filtered query will silently miss rows:

```sql
SELECT merchant, COUNT(*) AS n, MIN(date) AS first, MAX(date) AS last
FROM transactions
WHERE canonical_id IS NULL AND (LOWER(merchant) LIKE '%keyword%' OR LOWER(description) LIKE '%keyword%')
GROUP BY merchant ORDER BY last DESC;
```

To find every vendor whose name is spelled multiple ways in one pass, group by a normalized key (space-stripped uppercase prefix — the same rule the `possible_dupes` view uses):

```sql
SELECT SUBSTR(REPLACE(UPPER(merchant), ' ', ''), 1, 10) AS merchant_key,
       COUNT(DISTINCT merchant) AS variants, COUNT(*) AS n,
       GROUP_CONCAT(DISTINCT merchant) AS names
FROM transactions
WHERE canonical_id IS NULL
GROUP BY merchant_key
HAVING COUNT(DISTINCT merchant) > 1
ORDER BY variants DESC;
```

### Possible duplicate charges (cross-source pairs)

`canonical_id` dedup only links rows that share a `source_id`. The same purchase can still be recorded twice across pipelines — a card charge and its statement-PDF twin (`capone-…` vs `capone-csv-…`), or one trip's charges landing on two cards. The `possible_dupes` view flags candidate pairs: same amount (±$0.01), merchant fuzzy-matched, ≤3 days apart, excluding `-occurrence-N` siblings (those are intentional same-day purchases).

```bash
cashflow dupes                 # cross-account pairs only (double-post signature)
cashflow dupes --all           # include same-account identical repeats
cashflow dupes --json          # machine-readable
```

```sql
SELECT id_a, id_b, date_a, date_b, amount, days_apart,
       merchant_a, merchant_b, account_a, account_b
FROM possible_dupes
WHERE account_a != account_b
ORDER BY date_a DESC;
```

This is an advisory review list, not a deletion list: legitimate repeats also appear (two tanks of gas, a split dinner), and a flagged pair might be two real charges (e.g. one per subscription seat). Same-account same-amount pairs are usually two genuine purchases — that's why `--all` is opt-in. Confirm against the statements before removing anything; use the CLI for any mutation.

### Visit cadence for a repeating vendor (haircuts, oil changes, …)

Gap analysis with a window function (SQLite ≥ 3.25). Use the normalized merchant key from the recipe above so name variants don't break the sequence:

```sql
WITH visits AS (
  SELECT date, merchant,
         SUBSTR(REPLACE(UPPER(merchant), ' ', ''), 1, 10) AS mkey
  FROM transactions
  WHERE canonical_id IS NULL AND amount > 0
    AND SUBSTR(REPLACE(UPPER(merchant), ' ', ''), 1, 10) LIKE 'TOWNCENTER%'
)
SELECT date, merchant,
       ROUND(CAST(julianday(date) - julianday(LAG(date) OVER (ORDER BY date)) AS REAL) / 7, 1) AS weeks_since_previous
FROM visits
ORDER BY date;
```

The first visit shows a NULL gap. Average cadence, longest gap, and "days overdue vs. a target interval" are one more aggregation on top of this.

### Recurring charges of the same amount (subscription audit)

```sql
SELECT merchant, amount, COUNT(*) AS times,
       MIN(date) AS first_seen, MAX(date) AS last_seen,
       GROUP_CONCAT(DISTINCT strftime('%Y-%m', date)) AS months
FROM transactions
WHERE canonical_id IS NULL AND amount > 0
GROUP BY merchant, amount
HAVING COUNT(*) >= 3
ORDER BY last_seen DESC;
```

### Per-person spending

```sql
SELECT who, ROUND(SUM(amount - reimbursed_amount), 2) AS total
FROM transactions
WHERE canonical_id IS NULL AND strftime('%Y', date) = '2026'
GROUP BY who;
```

### Burn rate exactly as `cashflow status` computes it

```sql
-- month spending
SELECT ROUND(COALESCE(SUM(amount - reimbursed_amount), 0), 2)
FROM transactions
WHERE canonical_id IS NULL
  AND (category_id IS NULL OR category_id NOT IN
       (SELECT id FROM categories WHERE name IN ('Crypto/Investments','Investments','College Savings')))
  AND strftime('%Y-%m', date) = '2026-09';

-- month income
SELECT ROUND(COALESCE(SUM(amount), 0), 2) FROM income WHERE strftime('%Y-%m', date) = '2026-09';
```

`src/cashflow/queries.py` is the source of truth for these formulas.

### Amazon items linked to a transaction

```sql
SELECT t.date, t.merchant, t.amount, i.order_number, i.item_name, i.price, i.account
FROM amazon_items i
LEFT JOIN transactions t ON i.transaction_id = t.id
WHERE t.date >= '2026-01-01'
ORDER BY t.date DESC;
```

Unresolved orders have `transaction_id IS NULL`.

### Review queue depth

```sql
SELECT COUNT(*) FROM transactions WHERE canonical_id IS NULL AND status = 'pending';
```

## Gotchas

- **Deduplication is by `source_id`**, not by amount/date/merchant. Re-ingesting the same export is safe; two genuinely identical same-day purchases may both exist (Chase/Robinhood add occurrence suffixes, which the `possible_dupes` view deliberately ignores). Reconcile against statement totals before deleting anything. Cross-source near-duplicates (same purchase via two pipelines) are **not** linked — check `cashflow dupes` before counting a pair as two real charges.
- **The column is `account_id`** (integer FK into `accounts`), not `account`. Join `accounts` for card names and person attribution.
- **SQLite's `strftime` has no `%a`/`%A`** — day-of-week names silently return empty strings. Use `strftime('%w', date)` (0=Sunday…6=Saturday) or compute names in the shell: `date -j -f %Y-%m-%d 2026-08-18 +%a`.
- **Refunds are negative rows**, not an `is_refund` flag. Net-of-refund totals come from summing signed amounts; "spending" reports filter `amount > 0` or rely on the sign netting out.
- **Income is not in `transactions`** — it's a separate table filled only by the BofA checking paycheck pattern. Other deposits won't appear in surplus math.
- **`accounts` are buckets**, not physical cards (all BofA cards share one), so account freshness can't prove each card is current.
- **Vendors are spelled many ways** (`TOWN CENTER BARBER SHO` vs `Town Center Barber Shop`). Run the variant-discovery recipe above before any vendor query, or filter with the normalized merchant key.
- Write nothing by hand unless you understand the dedup/snapshot rules in [data-preservation.md](data-preservation.md); prefer the CLI (`cashflow tag`, `cashflow recategorize`, `cashflow rule set`) for mutations.
